Headline verdict

Trivially feasible, one structural fact drives the whole design: a browser page cannot read the filesystem, so “a search bar that runs docsearch” requires a local server process that does the searching on the page’s behalf. Everything else follows from keeping that server as small and safe as possible:

  1. Single file, Python 3 stdlib only (/usr/bin/python3 3.9.6, verified present) — no pip, no node, nothing to update. ~120 lines.
  2. Bound to 127.0.0.1 only — unreachable from the network by construction. Port 8377 verified free.
  3. Results open in the browser. Browsers block file:// links from http pages, so the server also serves the matched doc (with strict path guards). Clicking a result renders the runbook directly — arguably nicer than the terminal.

Item details

1. Server script STDLIB DONE 2026-07-05

Brief

File: ~/projects/docsearch/docsearch-server.py (location moved from ~/docs to a project folder at build time, 2026-07-05) — ThreadingHTTPServer(("127.0.0.1", 8377), …). The page lives separately at ~/projects/docsearch/index.html and is read per-request, so design tweaks don’t need a server restart. Three routes:

  • GET / — embedded single-page UI: autofocus search bar, result rows (title-ish filename, full path, modified date), styled like these runbooks. On load with an empty query it lists all runbooks newest-first.
  • GET /search?q=<words> — matches every query word, case-insensitively, as a substring of each doc’s home-relative path or stripped body text (empty q = the whole corpus), sorts by mtime desc, returns JSON [{path, rel, mtime}]. Answers carry X-Docsearch-Engine and X-Docsearch-Last-Scan headers. Changed 2026-07-31: this ran mdfind until Spotlight’s index went read-only — see spotlight-to-walk-migration.html.
  • GET /api/settings / POST /api/settings (added 2026-07-31) — the whitelist/blacklist rules behind the corpus, managed from the page’s ⚙ settings modal (gear button, or gs). Each rule is a folder name (docs), a full path (~/Documents/Codex — walked even outside the usual reach), or an exact filename (report.html); the server auto-detects the type. Blacklist always beats whitelist; hidden (dot) directories stay excluded unless a whitelisted path points inside one. Rules persist in settings.json next to the server (gitignored); when absent, built-in defaults reproduce the classic /docs/ behavior. Note the defaults now match folder names as exact segments, not substrings (my-node_modules-backup is no longer excluded). Every add/remove applies immediately: the server rescans (~2 s) before answering and the page refreshes the current search.
  • GET /view?p=<path> — serves the matched doc so results open with one click (see item 2 for guards). Since 2026-07-07 no longer what clicks use (kept for old bookmarks) — see next route.
  • GET /open?p=<path> (added 2026-07-07) — same guards as /view, then runs macOS open on the path so the doc opens in the default browser at its plain file:///… URL (see item 6).

Debounced live search (~250 ms) in the page JS, so results update as you type without re-running the match over the corpus on every keystroke.

Keyboard model (revised 2026-07-31) — ↑/↓ walk every runbook in painted order, not just the rows currently on screen, and open whatever was hiding the one they land on. So in grouped mode ↓ from a standing start expands only the first group and selects its first runbook; running off the end of a group steps into the next one (both levels under Folder+Date); ↑ re-enters the previous group at its last runbook. Groups stay open behind you — nothing shifts under the cursor, and gc still collapses everything. The selected row is held in the middle of the screen with scrollIntoView({block:'center'}), so there is always context above and below it; “middle where possible” comes for free, since the browser clamps scrolling at both ends of the document. Once the cursor is inside the first screenful the page snaps to the very top instead, so the header and search box come back rather than the first row sitting against the viewport edge with the chrome hidden above it (and ↑ at the top still scrolls even though the cursor cannot move further). Model layer: docEntriesOf (each doc + the head ids that hide it — the exact inverse of the visibleItems collapse filter) and navTarget in docsearch.js, both covered by test/docsearch.test.js.

Group-level keys (added 2026-07-31) — the cursor can also rest on a heading, which is what makes these possible: ⌘↓/⌘↑ jump group to group without expanding anything (from inside a group, ⌘↑ lands on its own heading first; ungrouped there are no headings, so they jump to the last/first runbook rather than being a dead key that also swallows the browser’s own ⌘↓); ← always moves the cursor to the row above, shutting the group you are leaving on the way out if it happens to be open — “above” being the previous group’s last runbook while that group is open, or its heading while it is shut, so repeated ← walks back up the index closing things behind you. Climbing out of a folder needs no special case: the row above a folder’s first date heading is the folder heading; → is the inverse and always means “go deeper” — open a shut heading, drop into an open one’s first runbook, or, on a runbook, open the document itself (same as ↩, and ⌘→ for a background tab); ↩ on a heading toggles it; gg/G jump to the first/last runbook; ⌘↩ opens in a background tab. ←/→ act whenever there is no query to edit — in an empty search box they are a no-op anyway, and the field is autofocused, so gating them on “field not focused” (tried first) left them dead in normal use. Once a query is typed they revert to caret movement and ⌘←/⌘→ take over as the group keys. Selection state is an index into the painted items (-1 = no cursor), and when a collapse hides the selected runbook the cursor retreats to the innermost heading still on screen rather than vanishing. Supporting model functions: headAbove, nextHead, firstDocUnder.

Coming back from a runbook (added 2026-07-31) — opening a runbook is a real same-tab navigation, so back (or a two-finger swipe) re-runs the page and would otherwise reset the query, the open groups, the cursor and the scroll. Chrome’s bfcache sometimes restores the live page instead, but it is evicted under memory pressure, skipped with devtools open, and gone once you have lingered — so the page snapshots {q, open[], sel, y} into sessionStorage on pagehide and restores it on load: the query and open groups are seeded before the fetch so the list paints in the right shape, then the cursor (re-found by path/id, never by index) and the scroll position are put back after the first paint. history.scrollRestoration is set to manual because Chrome’s own restore races the fetch and lands at the top. Session-scoped, not local: a brand new tab still opens on a clean index. An explicit ⌘R/⌃R resets the view and drops the snapshot — the load is told apart by performance.getEntriesByType('navigation')[0].type (reload vs back_forward, the latter reported for a swipe-back even when bfcache missed). Only view state resets; theme and the Folder/Date toggles are preferences in localStorage and survive, as settings should.

Keeping the list current (added 2026-08-02) — a file copied into a watched folder would not appear even after a reload, and that was the cache contract working as designed while being invisible. The corpus is held for SCAN_TTL = 45s and refreshed stale-while-revalidate: past the TTL, the request that notices the staleness still gets the old corpus and merely starts the ~2s walk on a worker thread. So a reload inside 45s rescans nothing, and a reload after it starts a scan whose result only the next request can see — the file always needed two reloads, and the status line (142 runbooks · newest first) read identically for a three-second-old index and a forty-minute-old one. Three parts now: the status row carries · indexed 2m ago from the server’s own X‑Docsearch‑Last‑Scan stamp (agoOf in docsearch.js; buckets are coarse and “just now” runs to 45s, wide enough that a walk plus a repaint does not read as 1m ago and make a successful refresh look like a no-op); a Re-sync link (gr) forces a synchronous walk via /search?fresh=1; and /search now answers with X‑Docsearch‑Rescanning: 1 whenever a walk is in flight behind the response, which the page treats as “fresher data is one request away” and quietly re-fetches 1.5s later — bounded to six tries, cancelled by typing. That last part is the root fix: new files now surface on their own a couple of seconds after any page load, and the link is the impatient path rather than the only one. Both repaints pass keepSel, which re-anchors the cursor after setDocs resets it — a re-scan of the same query moved nothing you were looking at, so the cursor must not move either; open groups need no help, because head ids are derived from the folder/date rather than from position. One race had to be closed first: _rescan() guarded its commit only against a rules change, so a background walk started before the new file existed could finish after the forced one, overwrite the fresh corpus and stamp _scanned_at late enough to suppress rescans for another TTL — resurrecting exactly the staleness Re-sync exists to end. Scans now take a start-order ticket and refuse to commit behind one that has already landed.

2. Path-guard security on /view MED DONE — guards verified 2026-07-05

Brief

Why this is the one MED: a file-serving endpoint is a directory-traversal foot-gun if unguarded. Guards (all must pass, else 403):

  • os.path.realpath(p) must be under $HOME (prefix check after resolution — defeats ../ and symlink tricks);
  • must end .html;
  • must contain /docs/;
  • must pass the same exclude pattern as search.

Net: the endpoint can serve exactly the set of files the search can return — nothing else. Combined with the 127.0.0.1 bind, exposure is limited to processes already running as you on this Mac (which could read those files anyway).

3. LaunchAgent LOW DONE 2026-07-05

Brief

File: ~/Library/LaunchAgents/com.mohsin.docsearch.plist (source copy kept in the project folder) — ProgramArguments = [/usr/bin/python3, /Users/dev/projects/docsearch/docsearch-server.py], RunAtLoad + KeepAlive, stdout/stderr → ~/Library/Logs/docsearch-server.log. Loaded immediately via launchctl bootstrap gui/$(id -u) <plist>; auto-starts at every login thereafter.

Ops: restart = launchctl kickstart -k gui/$(id -u)/com.mohsin.docsearch; stop for good = launchctl bootout gui/$(id -u)/com.mohsin.docsearch; full job state = launchctl print gui/$(id -u)/com.mohsin.docsearch.

How it runs at login (the launchd chain)
  1. launchd is macOS’s process manager — PID 1, the first process the kernel starts and the ancestor of everything else. Each logged-in user additionally gets a per-user launchd instance: that’s the gui/$(id -u) domain (gui/501) used in the ops commands above.
  2. At login, the per-user launchd scans ~/Library/LaunchAgents/, finds com.mohsin.docsearch.plist, and registers it as a job. Automatic — no Login Items, no shell, no cron.
  3. RunAtLoad=true → start the job immediately when it’s loaded, i.e. right at login. Without it the job would sit registered but idle until kicked.
  4. launchd executes ProgramArguments directly: /usr/bin/python3 /Users/dev/projects/docsearch/docsearch-server.py. No shell in between — .zshrc, aliases and env vars don’t apply, which is why both paths in the plist are absolute (a $HOME reference would fail silently).
  5. KeepAlive=true → launchd babysits the process forever: crash or kill → respawn (throttled to ~10 s). Seen live during setup: the port-conflict crash-loop self-healed the moment the blocking orphan died. Flip side: kill can never stop it permanently — only launchctl bootout can.
  6. stdout/stderr → ~/Library/Logs/docsearch-server.log per the plist — first stop when something’s off.

Note: the launchctl bootstrap run during setup was needed only once — the plist was created mid-session, after launchd’s login scan had already happened. From the next login onward, step 2 picks it up automatically.

LaunchAgents vs LaunchDaemons: agents (~/Library/LaunchAgents) run per user, at login, as you — right for docsearch (reads your files, binds a user port). Daemons (/Library/LaunchDaemons) run at boot, before any login, usually as root — wrong here: no $HOME context, needless privilege. Same plist format, different lifecycle.

6. Open results as plain file:// URLs STDLIB DONE — built & verified 2026-07-07

Brief

Request (2026-07-07): clicking a result should land on file:///Users/dev/….html, not http://localhost:8377/view?p=%2FUsers%2F….

Constraint (same one from the Headline verdict): browsers still block file:// navigation from an http page, so the page itself cannot open that URL. Instead the server opens it:

  • Server: new GET /open?p=<path> route — runs the same view_allowed() guards as /view (realpath under $HOME, .html, /docs/, exclude pattern; 403 otherwise), then subprocess.run(["open", realpath]). macOS opens the doc in the default browser at its file:// URL.
  • Page: openDoc() switches from window.open('/view?p=…') to fetch('/open?p=…').
  • /view stays (unchanged, still guarded) so previously bookmarked /view URLs keep working.

Trade-offs: docs now open in the default browser (may differ from where the search page is); the new tab comes from macOS, not the page, so no popup-blocker involvement. Bonus fix: relative cross-links between runbooks (e.g. doc-search-setup.html) 404’d under /view but resolve correctly under file://.

What gets worse (the honest part)

  1. A permanently running background process. Until now the search stack was zero-resident (Spotlight was already running anyway). This adds one python process (measured 2026-07-05: ~11–12 MB RSS, 0.0% CPU idle) that exists whether or not you use the page. On-demand mode was declined, but the rollback is one launchctl bootout.
  2. KeepAlive can loop. If the script is ever edited into a syntax error, launchd will respawn it repeatedly (throttled to ~10 s). The log file makes this obvious, but it’s a failure mode the pure-zsh setup didn’t have.
  3. A claimed port. 8377 is now spoken for on this machine; anything else wanting it will fail confusingly until you remember this server.
  4. Two implementations of one query. The include/exclude patterns now live in ~/.zshrc and the server. If you tweak one, tweak the other — noted in both files. Resolved 2026-07-31: the zsh function now calls /search, so the server is the only implementation.
  5. Same Spotlight dependency. Anything Spotlight can’t see (Privacy-listed folders, seconds-old files) is invisible here too — the web UI doesn’t fix that, it inherits it. Removed 2026-07-31 — and it bit first: the index went read-only and new runbooks silently stopped appearing. The server now walks the filesystem itself. What replaces it is smaller: up to 45 s of staleness, and folders macOS blocks the daemon from reading (~/Documents, ~/Desktop, ~/Downloads) are now named in the log instead of silently empty. See spotlight-to-walk-migration.html.
