docsearch — Spotlight → Filesystem Walk Migration

Related: doc-web-search.html (the original design & as-built record for this tool) · doc-search-setup.html (the terminal docsearch function; lives in ~/docs/)
Context: On 2026-07-31 a freshly written runbook (mobile-app-upstream-upgrade-runbook.html) was missing from the docsearch page. The file was fine; the Mac’s Spotlight index had gone read-only and had stopped accepting new files entirely.
Purpose: Record why the Spotlight dependency was removed, what replaced it, and how to roll it back.
Scope: docsearch-server.py (search engine), ~/.zshrc (docsearch() now queries the server), new test/test_server.py, doc updates. No change to the page, the model layer, the LaunchAgent, or the JSON contract.
Created: 2026-07-31 · SHIPPED & VERIFIED 2026-07-31 STDLIB

Symptom & diagnosis

A runbook that plainly existed on disk did not appear in the docsearch listing. The diagnosis ruled the tool out first, then the index:

ProbeResultReading
curl -o /dev/null -w "%{http_code}" .../view/<abs path> 200 The server can read the file and it passes every include/exclude rule. Not a filter problem.
mdls <file> every attribute (null) The file is not in the Spotlight index at all.
mdimport <file> no effect, still (null) Re-importing is a no-op — the index refuses writes.
mdutil -s /System/Volumes/Data “Index is read-only.” Root cause. Nothing new gets indexed, system-wide.
Write a throwaway .html into ~/docs, wait, mdfind it never appears Confirms it is not specific to one file or one folder.
Why this mattered more than one missing file. /search was 100% mdfind-backed, so docsearch’s completeness was exactly Spotlight’s health — and the failure mode is silent. Runbooks stop showing up and nothing reports an error. Two files in one folder were already affected (mobile-app-upstream-upgrade-runbook.html, mobile-app-nested-lists-runbook.html) before anyone noticed.

Decision

OptionVerdictWhy
Rebuild the Spotlight index (sudo mdutil -E -i on /System/Volumes/Data) USER’S CALL, SEPARATE Fixes the Mac (Spotlight search, Finder, Smart Folders) but leaves docsearch hostage to the next index wedge. Needs sudo and hours of background reindexing. Still worth doing for everything else on the machine.
Walk the filesystem in the server CHOSEN The corpus is ~71 files in a handful of predictable folders. Owning the index makes the tool immune to Spotlight’s state, and it retires the duplicated include/exclude rules between the server and ~/.zshrc. Cost: ~1.8 s per rescan, off the request path.

Engine design

PieceBehaviour
Scan os.walk($HOME), collecting .html files whose path contains /docs/ and misses the exclude pattern. Only .html: view_allowed() rejects anything else, so a .htm hit would 403 when clicked.
Prune Never descends into node_modules, Library, site-packages, venv, __pycache__, or any directory whose name starts with a dot. The include/exclude regexes are still applied per path afterwards — they remain the authoritative guard, shared with /view and /open.
Cache Corpus held in memory, TTL 45 s, stale-while-revalidate: a stale corpus is served immediately and the rescan runs on a worker thread, so no request ever waits on the walk. Only a cold start scans inline, and startup does that before the socket opens. Rescans are request-triggered, not on a timer, which preserves the tool’s 0% idle CPU.
Matching Every query word must appear, case-insensitively, as a substring of the home-relative path or the body text. Substring rather than whole-word because half these runbooks are named for build tags like cc18. Matching rel rather than the absolute path keeps “Users” and the username from matching everything. Filename-fragment queries are answered from the path alone, without opening any file.
Text extraction <script> and <style> blocks are dropped whole, then tags become spaces, then entities are unescaped. Dropping the style blocks is essential: these runbooks embed their CSS, so otherwise “grid” or “flex” would match every document. Per-file cache keyed on (mtime, size).
Diagnostics /search answers carry X-Docsearch-Engine: walk and X-Docsearch-Last-Scan. Each scan logs its doc count and names any folder it could not read — which is how a TCC block stops being invisible.

Why hidden directories are pruned

This is parity, not a shortcut. Spotlight never indexed dot-directories, so mdfind never returned anything from them. A walk that descends into them finds 51 extra files — all stale duplicate copies of real runbooks sitting in .claude-b/jobs/*/tmp/, .claude/worktrees/ and .git-worktrees/. Without dot-pruning the dashboard would have suddenly filled with duplicates of documents already listed.

Follow-up: the LaunchAgent interpreter (2026-07-31)

The first scans under the new engine reported six folders it could not read:

scan: 72 docs, unreadable: Desktop, Documents, Downloads, Movies, Music, Pictures

These are the TCC-protected folders. The LaunchAgent ran /usr/bin/python3, which is not an interpreter but a shim — it re-executes whichever Python lives in the active developer directory, so the process in ps was Xcode’s:

plist:            /usr/bin/python3
ps:               /Applications/Xcode.app/…/Python3.framework/Versions/3.9/…/Python
xcode-select -p:  /Applications/Xcode.app/Contents/Developer

That indirection is why an earlier attempt to grant Full Disk Access appeared to do nothing: the binary named in Privacy & Security and the binary actually being denied were not reliably the same, and a TCC grant keyed to Xcode’s Python would break on the next Xcode update anyway.

Fix: point ProgramArguments at Homebrew’s Python (/opt/homebrew/bin/python3, 3.14.6) — a real binary at a stable path, independent of Xcode. Because ProgramArguments changed, the agent needs a genuine reload; kickstart alone does not re-read the plist:

cp ~/projects/docsearch/com.mohsin.docsearch.plist ~/Library/LaunchAgents/
launchctl bootout   gui/$(id -u)/com.mohsin.docsearch
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.mohsin.docsearch.plist

Result: no Full Disk Access grant was needed. Homebrew’s Python already holds the access, and the unreadable: list disappeared on the first scan under it. Verified by writing a probe file to ~/Documents/docs/ and searching for a token that appears only in its body — the daemon returned it, proving it both walked and read a protected folder. Probe removed afterwards.

Caveat: a Homebrew major-version upgrade replaces the binary behind /opt/homebrew/bin/python3. If the unreadable: list ever returns to the scan log, that is the first thing to check. Note also that the first request after a restart can arrive before the startup scan finishes and the socket opens — give it ~3 s.

Rollback

cd ~/projects/docsearch
git log --oneline -3                 # find the walk-engine commit
git revert <commit>                  # server + tests + docs
launchctl kickstart -k gui/$(id -u)/com.mohsin.docsearch

The ~/.zshrc function is not under git — its previous body (the mdfind | grep | stat | sort pipeline) is quoted in the commit message and in this runbook’s history section. Reverting only makes sense alongside a working Spotlight index; the pre-migration behaviour is precisely what was broken.

Known limitations

  • TCC-protected folders stay invisible. Resolved 2026-07-31 — see the interpreter switch below. Every folder is now readable; the scan line is a plain scan: 72 docs with no unreadable: list.
  • Symlinked docs trees are not followed (followlinks=False) — same practical behaviour as before.
  • No phrase queries. Spotlight’s "exact phrase" quoting and its kind:/date: operators are gone. Word-AND substring is otherwise a superset of what Spotlight matched.
  • Up to 45 s of staleness. A runbook written seconds ago may need one refresh to appear. Previously this was unbounded, because the index never updated at all.
  • The Mac’s Spotlight index is still read-only. This change routes docsearch around it; it does not repair it. Finder search, Smart Folders and mdfind elsewhere remain affected until the index is rebuilt.

Glossary

docsearch
This tool: a small always-on local web page at http://localhost:8377 that lists and searches the HTML runbooks scattered across the home folder, plus a shell function of the same name that does the search from a terminal.
Spotlight
macOS’s built-in system-wide search index. It watches the disk and maintains a database of file names, metadata and text content so searches return instantly.
mdfind
The command-line interface to Spotlight. It queries the index only — it never reads the filesystem — which is why a broken index makes it return nothing for files that plainly exist.
mdutil / mdimport / mdls
The rest of the Spotlight command family: mdutil reports and controls indexing per volume, mdimport asks for a specific file to be re-indexed, mdls prints the indexed metadata for a file (all-null output means “not indexed”).
TCC — Transparency, Consent and Control
The macOS privacy subsystem that gates access to protected folders such as ~/Documents, ~/Desktop and ~/Downloads. A background process without permission gets errors rather than contents.
Full Disk Access — FDA
The System Settings permission (Privacy & Security) that exempts a named program from those TCC restrictions.
launchd / LaunchAgent
macOS’s service manager, and the per-user job description file it reads. The LaunchAgent com.mohsin.docsearch is what starts this server at login and restarts it if it exits.
launchctl kickstart
The command that restarts a launchd job. Required after editing the server’s Python; index.html and docsearch.js are re-read from disk per request and need only a browser reload.
TTL — time to live
How long a cached result is treated as current before it is refreshed. Here: 45 seconds for the file list.
Stale-while-revalidate
A caching strategy where an expired result is still served immediately while a fresh one is computed in the background — so the refresh cost never lands on a user’s request.
mtime
A file’s last-modification time, as recorded by the filesystem. docsearch sorts by it so the newest runbooks are listed first.
Corpus
The full set of documents the tool considers searchable — here, the 71 HTML files the walk collects.
Prune (in a directory walk)
Removing a directory from the list of places to descend into, so its entire subtree is skipped rather than examined and discarded.
git worktree
A second working directory checked out from the same git repository. Because it contains a full copy of the tracked files, it is a source of duplicate runbooks — hence the pruning.
